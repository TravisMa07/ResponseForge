## Source-derived compatibility boundary

C1 executes the complete client with Node24.21.0, TypeScript5.5.2 and a reviewed Axios1.17.0 candidate. That evidence does not establish the platform's own compiler or runtime compatibility. The independently inspected [dashboard platform](https://github.com/wazuh/wazuh-dashboard/tree/4a81e59ee597c0014e1d72666aa32423a964ba27) records Node18.19.0, Yarn1.22.19 and platform2.19.6/Wazuh4.14.10; its root lock selects Axios1.18.1. The plugin source remains commit `5005c3e2213abeb5c7798f489a7304a6abb7c6d1`.

The pinned platform's [server-file task](https://github.com/wazuh/wazuh-dashboard/blob/4a81e59ee597c0014e1d72666aa32423a964ba27/packages/osd-plugin-helpers/src/tasks/write_server_files.ts) invokes the [Babel transformation](https://github.com/wazuh/wazuh-dashboard/blob/4a81e59ee597c0014e1d72666aa32423a964ba27/packages/osd-dev-utils/src/babel.ts). It disables babelrc/config-file discovery, supplies the actual upstream node preset and enables inline source maps. That preset targets Node14 while execution uses the platform-selected Node18.19.0; these are distinct settings and must not be silently equated. Its actual common preset supplies TypeScript/React transforms and shared plugins. Replacing this chain with TypeScript transpileModule or a hand-written subset does not meet the C2 compiler claim.

C2 qualifies platform-source-bound emission and real client transport compatibility only. A minimum locked toolchain is not a complete bootstrapped workspace or the actual dependency tree installed in an image. Full plugin archive creation, optimization, production dependency installation/hoisting, semantic TypeScript checks, deployed dependency resolution, Linux/image execution, manager bootstrap/capture and endpoint proof remain separate. Deployment must retain `ready=False`.

## Real emission and transport oracle

The complete original and corrected ServerAPIClient and actual cookie helper must emit through the reviewed Babel pipeline and load with real Axios under Node18.19.0. Constructor-protocol fixtures may stand in for logger/ManageHosts/security collaborators, as in C1; Axios, HTTPS agent, TLS sockets and HTTP exchange must remain real. Do not extract or reconstruct only the modified constructor for a compatibility claim. Do not remove unrelated upstream duplicate `_axios` declarations to hide a compilation limitation.

The existing 13-scenario matrix is retained: original insecure baseline; trusted CA/matching SAN; missing CA; different CA; untrusted chain; wrong SAN; NODE_TLS_REJECT_UNAUTHORIZED=0; plain HTTP; embedded URL credentials; control-character URL; HTTPS redirect; HTTP redirect; hostile proxies. Both authentication and authenticated request paths are exercised in each applicable scenario.

| Observable case | Independent required observation |
| --- | --- |
| Original complete client against an untrusted fixture certificate | Module actually loads and performs one authentication and one request HTTP exchange; explicitly record the failed secure expectation and insecure baseline separately from corrected success |
| Corrected client, trusted CA and matching SAN | Both paths succeed with original Basic identity/cookie-derived Bearer authority; forged caller authorization and nonallowlisted headers do not replace server authority |
| Missing/different CA, untrusted chain, wrong SAN or global TLS-disable environment | Assert the specific expected native TLS/name refusal category and zero application HTTP/credential observations on every listener; generic runtime failure is insufficient |
| Plain HTTP, embedded credentials or control-character URL | Assert the reviewed URL-policy refusal and zero HTTP/credential observations; an unrelated TypeError is insufficient |
| HTTPS or HTTP redirect | Observe the initial redirect response, require no follow, and record zero redirect-target contacts |
| Hostile proxy variables without NO_PROXY exemption | Direct legitimate HTTPS succeeds; every proxy listener records zero contacts. Record runtime support separately: Node18's behavior cannot establish Node24 environment-proxy mode support |
| Babel emission, require/import, dependency setup or child-process failure | Qualification fails as setup/compiler/execution failure; retain diagnostics separately and never count it as an intended TLS refusal |

Startup CA variants require fresh actual child processes because NODE_EXTRA_CA_CERTS is launch-time policy. The harness binds fixtures only to loopback, creates ephemeral original certificates privately, stops all listeners in finally and leaves the OS trust store unchanged. No manager, Docker service or endpoint operation follows from this test.
