## Bounded slices and acceptance boundary

RF-05A implements domain assessment and authenticated durable prepare/gate/dispatch steps against the common core, with independent offline tests. It uses Refs#5. RF-05B owns the bounded native task app, reviewed worker allowlist extension, actual importable graphs and real three-workflow qualification. Only RF-05B can close#5 after genuine execution, approval denial/expiry, unsupported escalation, callback loss and restart proof. No offline task, diagram or one-node Python orchestration counts as a real Shuffle playbook. No external data or endpoint action is introduced.

Shuffle will own sequencing/branches: prepare → gate; await human decision/explicit resume, dispatch only on approved branch → final callback. There must be one final responseforge_callback1.0.0/callback node in the entire graph; branches converge there. FINISHED/native result/core callback and endpoint verification remain distinct. No automatic human approval, caller-selected action/target/provider, raw URL/key/command parameters or blind response retry. RF-05B uses the same core and replay contracts on Desktop/guest; every target needs its own proof.

## Frozen RF-05A interfaces

Primary owns `playbooks/models.py`, runtime Settings, API wiring, contracts/schemas/locks/CI/shared docs and integration. Pure writer owns only `playbooks/assessment.py`; service writer only `playbooks/service.py`; independent test writer only `tests/rf05/**`. No Docker operations by agents. Shared files have one writer. All handbacks name base/changed files/commands/results/failures/objections.

`PlaybookKind = Literal["process", "persistence", "containment"]`. `PlaybookStepRequest` extends ShuffleArgument with workflow_id(UUID). Kind comes only from server Settings.playbook_bindings (workflowUUID→kind), never request. Body incident_id must match path. `Assessment` has kind, disposition(propose|escalate|no_action), action(optional ActionType), resource(optional Id), rationale(Id), event_ids(tuple Id), known_gaps(tuple Id). Only propose carries both action/resource. `assess(kind,batch,alert)->Assessment` is pure, validates detached inputs and exact alert/source binding, and filters exact endpoint/scenario and alert±5minutes; source fields are never commands. Caller-provided fields cannot replace registered evidence.

`PlaybookPlan` has record_type=playbook_plan, request, kind, source_sha256, assessment, evidence_refs, known_gaps, proposal_id(optional), provider, provider_version, created_at, readiness_event_id. `PlaybookProgress` has request, kind, status(no_action|awaiting_approval|denied|expired|ready|uncertain|completed|failed), proposal_id(optional), execution(optional ActionExecution).

Settings additions (empty/None defaults keep old routes unchanged): playbook_bindings:dict[str,str], playbook_actors:dict[str,str] mapping analyst/executor→configured actor IDs, playbook_provider:str|None. These are trusted server configuration, copied/validated. Bindings must be a subset of reviewed Shuffle bindings; kinds exact. If configured, both technical actors must exist, have their exact single role, human=false; no approver authority. Workflow caller must be exactly workflow role/human=false, scoped to the case. It cannot obtain the separate technical credentials or a human credential. The bound step facade invokes existing core operations under those configured principals; no role mutation/caller-supplied approval. Internal operation audits identify technical actors, plus a bound playbook audit identifies triggering workflow actor/run.

`PlaybookService(core:CaseService)` exposes async prepare(incident_id,request,actor)->PlaybookPlan, gate(...)->PlaybookProgress, async dispatch(...)->PlaybookProgress. API POST `/v1/incidents/{incident_id}/playbooks/{prepare|gate|dispatch}` authenticates the workflow credential and accepts only PlaybookStepRequest. All source/case/run/workflow/correlation/mode/binding/provider/principal checks precede evidence/proposal/provider mutation. Replay only; missing qualified source/provider/config or live mode fails explicitly. Require original matching PlaybookRun and Shuffle DeliveryRecord reservation, configured version/graph/origin, and running run for new mutations. Cached plan/execution reads still revalidate bindings; terminal run cannot authorize a new effect.

Plans use `callbacks` namespace `playbook-plan:<run_id>`; revalidate stored contracts/scope/source on every read. No storage migration. Duplicate prepare returns the original plan/proposal/expiry/readiness. Proposal ID is deterministic over case/kind/source/action/resource (not run), so another workflow delivery cannot create another action effect. Recover a partially prepared original proposal without renewing its TTL; immutable conflicts reject. Evidence collection uses all four fixed artifacts and server-selected±5minute window through CaseService.collect; preserve available provenance and explicit gaps. Advance only RECEIVED→TRIAGING→INVESTIGATING as needed; never fabricate containment/resolution. Create proposal only after trusted pinned provider capability lookup agrees on mode/action/version/support; unsupported escalates; lookup failure/timeout is unavailable503, never unsupported/success. Existing core rechecks everything at dispatch.

Readiness requires actual available source-linked evidence, known gaps, proposal or no-action reason and original alert_accepted audit ID. Mark once with deterministic sorted evidence/gaps and original immutable proposal; conflicting existing readiness is409 rather than relabeled. Case-ready metrics use existing core revision/environment/correlation. No analyst-time savings or latency benchmark is inferred.

Gate reads server-stored action/decision; none→awaiting, rejected/cancelled→denied, expired proposal/approval→expired, current approved→ready. No effect. Dispatch revalidates through CaseService.execute; an expiry race must reject there. Existing unknown/pending execution uses reconcile only; original provider/version/target must match, never redispatch. Verified execution→completed with explicit simulation flags, known failure→failed, uncertain result→uncertain. Existing verified effect is not erased by later approval expiry. No proposal→no_action. Denied/expired dispatch must audit and produce no provider execute/effect.

## Deterministic evidence conditions

Process: original RF03 hidden encoded PowerShell rule; exact process event at alert time with canonical positive PID≤2147483647 and process GUID proposes terminate_process/process:PID. Suspicious but missing target identity escalates. Missing recorded parent gives a gap; unrelated/benign process yields no_action. No external reputation provider: explicitly annotate offline reputation unavailable.

Persistence: persistence event with task_name or service_name, account, process_guid and same-scope recorded matching process can recommend disable_persistence with resource persistence:<digest-of-identifier>. Missing actor/association/identifier escalates. Current mock has no disable_persistence capability, so prepare must honestly escalate unsupported and never create/execute that proposal. No fake disablement or new provider capability is introduced.

Containment: same-scope recorded process GUID associated with either an outbound network event with destination_ip/domain and the process's same hidden encoded PowerShell condition, or a file event operation=shadow_copy_delete. These are narrow original recorded indicator rules, not broad ransomware/C2 detection claims. Propose isolate_host/resource host:<endpoint_id> with impact and unisolate rollback guidance in rationale. Missing association/artifact escalates; benign unrelated data no_action. Only a qualified replay mock can support it here; live is not implemented by this slice.

Pre-implementation refinement: existing mock provider `_allowed` requires `host:<endpoint_id>`; the draft bare `host` resource is corrected to the proven adapter contract, with no mock capability change.

Pre-implementation refinement: Plan explicitly stores provider_version so restored/cached steps reject a changed provider pin instead of silently reusing current configuration. No sidecar key or implicit version inheritance.

Integration review refinement before correction: a run can become terminal while existing core capability I/O is awaiting. A pre-step check alone cannot authorize a new reservation. Add an optional trusted internal `CaseService.execute(..., pre_dispatch:Callable[[Transaction],None]|None=None)` guard, invoked inside the final reservation transaction after an existing execution short-circuits. RF05 facade revalidates original run/delivery scope and running/nonterminal state through that transaction, with no I/O/nested transactions. This callback is never an HTTP parameter or source-data code. Independent race regression must fail before implementation; core still independently revalidates approval/capability. Existing uncertain verification does not create a new dispatch and remains recoverable.

## RF-05B preparation from the proven step interfaces

Keep domain tasks separate from the single final native callback. The task adapter will accept only fixed prepare/gate/dispatch actions and original execution argument; core URL/key/CA come from private configuration, never workflow data. Worker allowlist changes must match exact reviewed app/version/action and immutable image. Investigate the pinned vendor branch-condition/import wire format before freezing actual graph JSON; do not infer it from an untested example.

Human waiting is a business outcome, not an unknown-delivery retry. A graph may complete its investigation branch with an awaiting/denied/expired/no-action outcome and no response effect. An explicit later invocation after a separate core human decision can reuse the same case/kind/source-derived proposal, readiness and original expiry; it cannot reset approval or create a second effect. A real lost vendor-start acknowledgement still reconciles only the original UUID and never invokes this explicit-new-run path automatically. An offline cross-invocation test confirms original proposal/readiness and one durable simulated effect; real Shuffle branch/resume proof remains RF-05B.
