## Observed FINISHED semantics and native receipt binding

A genuine deliberately failing app produced native FAILURE while the vendor workflow was FINISHED, despite exit_on_error. Vendor terminal status proves completion; it does not establish success. VendorExecution and durable DeliveryRecord therefore expose only a sanitized `callback_status` from exactly one native result for the reviewed responseforge_callback1.0.0/callback action, bound to that graph node's ID/app metadata and original execution ID. Missing/duplicate/mismatched/unknown receipts remain unverified. No result body or execution authorization is retained in this projection.

Finalization needs the executed graph, native action result and authenticated core node observation to agree. FINISHED/SUCCESS plus nativeSUCCESS/core succeeded finishes. Any vendor terminal completion plus nativeFAILURE/core failed or timeout fails, retaining the actual vendor status. NativeFAILURE/core succeeded is uncertain (including real post-commit acknowledgement loss), as is vendor FAILURE/ABORTED with nativeSUCCESS. This replaces the earlier assumption that deliberately failing native actions necessarily make vendor status FAILURE.
